## 摘要

ADR（Architecture Decision Record，架構決策記錄）是一份簡短文件，用來回答：

> 我們在什麼背景下，為什麼選擇這個方案，而不是其他方案？

它重點不是描述整套系統，而是保存「決策當下的理由」，避免幾個月後只看見結果，卻沒人知道原因。

## 如何使用 ADR

當一項決策具備以下特徵時，適合建立 ADR：

- 會長期影響系統架構
- 未來不容易撤回或修改成本很高
- 曾有多個合理選項
- 團隊可能再次質疑或討論
- 涉及安全性、成本、效能或合規要求

例如：

- 選 PostgreSQL 還是 MongoDB
- 採用微服務還是模組化單體
- 是否使用雲端 LLM API
- 敏感資料能否送到外部 AI 服務
- 採用 RAG、微調或純 Prompt

不需要替每個小決定建立 ADR，例如變數命名、按鈕顏色或普通套件升級。

## 基本流程

1. 發現需要做出重要決策
2. 建立一份狀態為 `Proposed` 的 ADR
3. 記錄背景、限制及候選方案
4. 討論並選擇方案
5. 將狀態改為 `Accepted`
6. 實作後持續保留，不直接覆寫歷史
7. 決策改變時建立新 ADR，將舊 ADR標記為 `Superseded`

常見狀態包括：

- `Proposed`：提案中
- `Accepted`：已接受
- `Rejected`：未採用
- `Deprecated`：已不建議使用
- `Superseded`：被另一份 ADR 取代

## ADR 範例

```markdown
# ADR-001：使用 PostgreSQL 作為主要資料庫

- 狀態：Accepted
- 日期：2026-06-24
- 決策者：開發團隊

## 背景

系統需要交易一致性、複雜查詢及成熟的備份機制。

## 考慮的方案

1. PostgreSQL
2. MongoDB
3. MySQL

## 決策

採用 PostgreSQL。

## 理由

- 支援完整交易
- 團隊已有維運經驗
- 適合目前以關聯資料為主的模型

## 影響

### 正面

- 資料一致性較容易維護
- 可使用成熟的 SQL 工具

### 負面

- Schema 變更需要管理 migration
- 水平擴展較複雜

## 後續行動

- 建立 migration 流程
- 制定備份與還原策略
```

ADR 應記錄當時已知的事實與取捨，而不是事後把決策寫得看似完美。

## ADR 與 AI 的關聯

### 1. 記錄 AI 系統的重要決策

AI 系統有許多不容易從程式碼看出的選擇，例如：

- 為何選某個模型或供應商
- 為何使用 RAG 而不是微調
- 哪些資料可以傳給模型
- Prompt 和模型版本如何管理
- 如何處理幻覺、偏見與錯誤輸出
- 是否允許 AI 自動執行外部操作
- 如何設定人工審核與回退機制
- 如何評估準確率、延遲與成本

這些決策通常同時涉及技術、風險、隱私及商業考量，很適合用 ADR 保存。

### 2. 為 AI Agent 提供長期背景

程式碼告訴 AI「系統目前怎麼做」，ADR 則告訴 AI「為什麼這樣做」。

把 ADR 提供給 AI Agent，可以減少它：

- 重複提出已被否決的方案
- 修改程式時破壞架構原則
- 不知道隱私或合規限制
- 把刻意設計的行為誤認為技術債

因此 ADR 可視為提供給人類和 AI 的「架構記憶」。

### 3. 使用 AI 協助撰寫 ADR

AI 可以協助：

- 從會議記錄提取決策與理由
- 補充可能遺漏的替代方案
- 比較成本、風險及維護性
- 將討論整理成統一格式
- 檢查不同 ADR 是否互相衝突

但最終決策與責任仍應由人承擔。AI 可能補出會議中不存在的理由，因此產生的 ADR 必須經過決策者確認。

簡單來說：

> 程式碼保存實作，ADR 保存意圖；AI 可以協助整理意圖，也可以透過 ADR 更準確地理解系統。
