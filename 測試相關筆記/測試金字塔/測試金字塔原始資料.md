## 內容摘要

`ssstool 補測試筆記` 中的「測試金字塔」段落，把測試金字塔整理成 Unit Test、Integration Test、UI / E2E Test 三層。它的核心說法是：越底層的測試數量越多、執行越快、成本越低；越上層的測試越接近真實使用情境，但也更慢、更脆弱、更貴。

該段落也提醒，測試金字塔不是要否定 E2E，而是要求精準使用 E2E。大量單元測試可以快速保護商業邏輯與邊界條件，適量整合測試確認模組合作，少量 E2E 測試則用來驗證最重要的使用者流程。

## 原始內容

測試金字塔是一種軟體測試策略模型，用來說明「不同層級的測試應該如何分配比例」。核心觀念是：越底層的測試數量越多、執行越快、成本越低；越上層的測試數量越少、越接近真實使用情境，但也更慢、更脆弱、更貴。

常見結構如下：

```
UI / E2E 測試
Integration 測試
Unit 測試
```

**1. Unit Test，單元測試**

單元測試位於金字塔底部，數量應該最多。

它測試的是最小單位的程式邏輯，例如一個 function、一個 class、一個 module。通常不依賴資料庫、網路、外部 API 或真實 UI。

特點：

- 執行速度快
- 維護成本低
- 容易定位錯誤
- 適合測試商業邏輯、邊界條件、例外處理

例如：

```
計算折扣金額是否正確
驗證 email 格式是否通過
訂單狀態轉換是否合法
```

**2. Integration Test，整合測試**

整合測試位於中間層，數量比單元測試少。

它測試多個元件之間是否能正確合作，例如 service 與 database、API 與 repository、前後端資料格式、訊息佇列與消費者之間的互動。

特點：

- 比單元測試慢
- 能發現元件接合處的問題
- 適合測試資料流、API contract、資料庫操作
- 錯誤定位比單元測試稍難

例如：

```
建立訂單 API 是否正確寫入資料庫
登入流程是否能正確查詢使用者並產生 token
付款成功事件是否會更新訂單狀態
```

**3. UI / E2E Test，端對端測試**

E2E 測試位於金字塔頂端，數量應該最少。

它模擬真實使用者操作完整系統，例如打開瀏覽器、輸入帳密、點擊按鈕、完成購物流程。

特點：

- 最接近真實使用情境
- 執行速度慢
- 容易因 UI 改動、網路、環境不穩而失敗
- 維護成本高
- 適合測試關鍵流程，而不是覆蓋所有細節

例如：

```
使用者註冊並登入成功
加入商品到購物車並完成結帳
管理員建立報表並下載
```

**為什麼叫「金字塔」？**

因為理想的測試分布應該像金字塔：

```
少量 E2E 測試：確認核心使用流程
中量整合測試：確認模組合作正常
大量單元測試：確認細節邏輯正確
```

也就是說，不應該把大部分測試都寫成 E2E。那樣會變成「倒金字塔」，測試會很慢、很不穩、很難維護。

**測試金字塔的主要價值**

它幫助團隊在「信心」與「成本」之間取得平衡。

單元測試便宜快速，但不能保證整個系統真的能跑。E2E 測試信心高，但慢又脆弱。所以好的策略是：用大量底層測試快速保護邏輯，用少量高層測試確認關鍵流程。

**簡單比例參考**

實務上沒有固定比例，但可以用這個方向理解：

```
Unit Test：最多，約 60% ~ 80%
Integration Test：中等，約 15% ~ 30%
E2E Test：最少，約 5% ~ 10%
```

這不是硬規則，要依系統類型調整。例如金融、醫療、基礎建設系統可能需要更多整合與驗收測試。

**常見誤解**

測試金字塔不是說 E2E 不重要，而是說 E2E 應該精準使用。

也不是說單元測試越多越好。如果單元測試只測 implementation details，反而會讓重構變困難。好的測試應該保護行為，而不是綁死內部寫法。

**一句話總結**

測試金字塔是一種測試分層策略：用大量快速穩定的單元測試保護細節，用適量整合測試驗證模組合作，用少量 E2E 測試確認最重要的使用者流程。
