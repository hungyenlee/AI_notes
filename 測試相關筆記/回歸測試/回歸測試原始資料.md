## 原始資料

回歸測試（Regression Testing）是指：當你修改程式後，重新測試既有功能，確認原本正常的東西沒有被新變更弄壞。

常見情境像是：

- 修 bug 之後，確認 bug 修好了，也確認其他功能沒壞
- 新增功能後，確認舊功能仍然正常
- 重構程式碼後，確認外部行為沒有改變
- 升級套件或框架後，確認系統仍能如預期運作

簡單說，回歸測試是在問一句話：

「這次改動有沒有不小心破壞以前已經可以運作的功能？」

例如一個購物網站新增折扣碼功能後，除了測折扣碼本身，也要測原本的「加入購物車」、「結帳」、「付款」、「訂單成立」是否仍然正常。這些就是回歸測試的一部分。

回歸測試的核心精神其實很樸素：保護已經被證明可用的行為，不被新的改動意外破壞。

它不是單純「多跑一些測試」，而是一種工程上的保險機制：每次系統改變，都要確認那些原本可靠的功能仍然可靠。

「回歸」的意思是：系統退回到以前曾經出現過的錯誤狀態，或是原本正常的功能又壞掉了。

例如：原本登入功能正常，工程師後來修改了會員資料頁面，結果因為共用了一段驗證邏輯，登入功能突然壞掉。這就是一種「回歸」：不是新功能本身壞，而是舊功能被新的改動牽連了。

所以回歸測試就是在修改後檢查：

- 原本修好的 bug 有沒有復發
- 原本正常的功能有沒有壞掉
- 原本承諾給使用者的行為有沒有改變
- 系統在常見流程中是否仍然穩定

軟體不是一堆彼此獨立的零件，而是一張互相連動的網。你改 A，可能影響 B；你修 bug，可能破壞某個例外情境；你重構程式，可能不小心改變資料格式；你升級套件，可能讓舊 API 行為不同；你新增欄位，可能讓舊報表查詢失敗。

很多錯誤不是出現在「你正在改的地方」，而是出現在「你以為不會受影響的地方」。回歸測試就是專門抓這類問題。

回歸測試的核心精神可以分成四層：

第一，守住既有承諾。一個系統只要已經上線、已經有人使用，它就對使用者形成了承諾。例如使用者可以登入、訂單可以成立、報表數字正確、API 回傳格式穩定、權限規則照舊生效、過去修掉的錯誤不要再出現。回歸測試是在守住這些承諾。它關心的不是「程式碼有沒有改得漂亮」，而是「使用者依賴的行為是否還在」。

第二，讓改動變得可承受。沒有回歸測試的系統，工程師會越改越怕，因為每次修改都可能破壞未知的地方，而且不知道什麼時候才會爆。久了之後，團隊會不敢重構、不敢升級、不敢快速交付。有回歸測試後，改動就比較可承受：改完可以快速驗證、錯誤可以早點發現、重構比較有底氣、發版前比較不靠運氣、團隊比較敢持續改善系統。所以回歸測試不只是找 bug，它是在降低「改變」的成本。

第三，把過去的教訓留下來。每一個曾經發生過的 bug，其實都是系統給你的情報。如果某個 bug 修完之後沒有加測試，那它很可能未來又會回來。如果修完 bug 的同時補上一個測試，那這個測試就像是在系統裡放了一個警報器：只要這個錯誤再出現，就立刻提醒。好的回歸測試會把過去踩過的坑變成未來的防線。這也是它很重要的精神：不要白白浪費錯誤。

第四，驗證行為，而不是迷信實作。回歸測試真正要保護的是「外部可觀察的行為」，不是每一行程式碼的長相。例如你重構登入邏輯，內部程式可以完全不同，但只要正確帳密可以登入、錯誤密碼不能登入、停用帳號不能登入、登入後 session 正確建立、錯誤訊息符合預期，那系統行為就是穩定的。

回歸測試通常會測：

- 核心業務流程：登入、結帳、付款、下單、匯出、搜尋
- 曾經出錯的 bug：修好後補一個測試，避免復發
- 高風險模組：金流、權限、資料同步、計價、庫存
- 常被修改的地方：需求常變的功能容易被改壞
- 系統整合點：API、資料庫、第三方服務、排程任務
- 邊界條件：空資料、大量資料、特殊權限、異常輸入

不是所有東西都要測到滿，而是優先測那些「壞掉代價高」或「很容易又壞」的地方。

假設你有一個電商系統，原本有使用者登入、加入購物車、使用優惠券、計算運費、結帳付款、產生訂單。某天你修改「優惠券」邏輯，新增「滿 1000 折 100」。你不能只測滿 1000 有沒有折 100，還應該確認沒滿 1000 不會折扣、舊優惠券仍然可用、運費計算沒有被折扣邏輯弄錯、訂單總金額正確、付款金額和訂單金額一致、已失效優惠券不能使用、原本修過的優惠券 bug 沒有復發。

回歸測試不是一種固定層級的測試，而是一種測試目的。它可以是單元測試、整合測試、API 測試、E2E 測試、手動測試或自動化測試。所以「回歸測試」不是和「單元測試」並列的分類。更精確地說，回歸測試是：為了避免舊功能退化而執行的一組測試。

常見執行時機包括：修 bug 後、新增功能後、重構後、合併分支前、發版前、升級依賴套件後、修改共用元件後、修改資料庫 schema 後、改動權限、計價、金流、驗證邏輯後。改動越接近核心流程，越需要回歸測試。

好的回歸測試通常針對重要行為，不只是追求數量；能穩定重現，不會一下過一下失敗；跑得夠快，至少常用的一組能頻繁執行；失敗時能指出哪個行為壞了；會隨著產品變化更新；對曾經發生過的 bug 有明確防線；不過度依賴內部實作細節。

常見誤解包括：回歸測試就是全部重測。其實不一定，完整回歸有時需要，但日常更常見的是根據風險挑選測試範圍。只有自動化才叫回歸測試也不對，手動也可以是回歸測試，只是自動化更適合頻繁重複執行。測試通過也不代表完全沒問題，它只能證明「有被測到的行為目前符合預期」。回歸測試也不是越多越好，太慢、太脆弱、太難維護的測試會變成負擔，重點是有效防守高風險行為。

一句話總結：回歸測試的核心精神是，把系統已經建立起來的可靠性保存下來，讓每一次修改都不會用新的進步換掉舊的穩定。

或者更工程一點地說：它是把過去驗證過的正確行為，變成未來每次變更時都會自動檢查的安全網。
