## 原始資料

這三個可以理解成：**QA 從「執行測試」往「判斷品質與風險」靠近時，會越來越常做的事。**

## 1. Exploratory Testing：探索式測試

**意思：**
不是照著事先寫好的 Test Case 一步一步測，而是測試人員一邊使用系統、一邊觀察、一邊產生新的測試想法。

比較像：

> 我先知道這個功能大概要做什麼，然後像真實使用者一樣操作，邊測邊找可疑的地方。

例如一個登入功能，固定 Test Case 可能是：

| 測試項目 | 操作 |
| ------ | -------- |
| 正確帳密登入 | 輸入正確帳號密碼 |
| 錯誤密碼登入 | 輸入錯誤密碼 |
| 空白欄位 | 不輸入帳密 |

但 Exploratory Testing 可能會想：

* 密碼輸錯很多次會怎樣？
* 開兩個分頁同時登入會怎樣？
* 登入到一半網路斷掉會怎樣？
* Token 過期後按上一頁會怎樣？
* 手機版和桌機版行為是否一致？
* 錯誤訊息會不會洩漏太多資訊？

所以它的重點不是「沒有規劃」，而是：

> 有方向地探索未知風險。

---

## 2. Risk Analysis：風險分析

**意思：**
在測試前先判斷：**哪些地方最容易出問題？哪些地方出問題影響最大？**

因為時間有限，不可能什麼都測到最完整，所以要決定測試優先順序。

常見會看兩個維度：

| 維度 | 問題 |
| ---- | --------------------------- |
| 發生機率 | 這裡容易壞嗎？最近有改嗎？邏輯複雜嗎？ |
| 影響程度 | 壞了會很嚴重嗎？會影響付款、資料、安全、正式使用者嗎？ |

例如一個電商網站改版：

| 功能 | 風險判斷 |
| ------------ | ---- |
| 首頁 Banner 改字 | 風險低 |
| 購物車折扣邏輯 | 風險高 |
| 付款流程 | 風險很高 |
| 後台顏色調整 | 風險低 |
| 會員資料同步 | 風險高 |

所以 QA 或工程師會把更多測試資源放在：

* 付款
* 訂單
* 權限
* 資料寫入
* 第三方 API
* 最近改動大的地方

一句話：

> Risk Analysis 是決定「哪裡值得花最多力氣測」。

## 3. Release Strategy：發布策略

**意思：**
決定一個版本要怎麼安全地上線，而不是只問「測完了沒」。

它關心的是：

> 這個版本要怎麼推出，才能降低上線風險？

例如：

### 常見 Release Strategy

| 策略 | 說明 |
| --------------------- | ----------------------------- |
| Big Bang Release | 一次全部上線 |
| Blue-Green Deployment | 新舊環境並行，確認後切換流量 |
| Canary Release | 先給少量使用者用，沒問題再逐步放大 |
| Feature Flag | 功能先部署，但用開關控制是否開放 |
| Rollback Plan | 如果壞了，怎麼快速退回上一版 |
| Staged Rollout | 分批釋出，例如 5% → 25% → 50% → 100% |

例如你之前問過 Blue-Green：

不是只有「測 Green 沒問題就切過去」，實務上還會搭配：

* 上線前自動化測試
* Smoke Test
* 小流量驗證
* 監控錯誤率
* 觀察 log / metrics
* 有問題快速 rollback

所以 Release Strategy 的重點是：

> 測試不是結束在「測完」，而是要設計「怎麼安全上線」。

## 三者差異簡單整理

| 名稱 | 核心問題 | 主要目的 |
| ------------------- | ----------- | ------ |
| Exploratory Testing | 還有什麼沒想到的問題？ | 發現未知問題 |
| Risk Analysis | 哪些地方最值得優先測？ | 決定測試重點 |
| Release Strategy | 怎麼安全地上線？ | 降低發布風險 |

可以把它們放在一個流程裡看：

```text
Risk Analysis
先判斷哪裡風險最高
        ↓
Test Planning / Automation
針對高風險區域設計測試
        ↓
Exploratory Testing
人工探索自動化測試沒涵蓋的問題
        ↓
Release Strategy
決定怎麼安全推出版本
```

## 跟 AI Testing 的關係

AI 可以幫忙：

* 產生測試案例
* 找邊界條件
* 分析 log
* 建議可能風險
* 產生 regression tests

但這三件事目前還是很需要人的判斷：

* 哪些風險真的重要？
* 哪些使用情境值得探索？
* 這個版本能不能上線？

所以我前面才會說，AI 時代 QA 的價值會更靠近：**品質判斷、風險判斷、上線判斷**。
