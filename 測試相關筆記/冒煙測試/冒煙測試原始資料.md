## 原始整理

Smoke Testing，又常被翻成「冒煙測試」，是一種在新版本、部署或建置完成後，先快速檢查核心功能是否還能正常運作的測試。

它的重點不是把系統測完整，而是先回答一個很務實的問題：

> 這個版本有沒有壞到不值得繼續測試？

如果 Smoke Testing 失敗，通常代表目前 build 或部署環境有明顯問題，應該先修正，而不是繼續投入更完整、更耗時的測試。

## 為什麼叫 Smoke Testing

這個名稱來自硬體測試的比喻：設備通電後，如果立刻冒煙，就表示它有嚴重問題，根本不需要進一步測試。

放到軟體測試裡，Smoke Testing 的意思就是：

> 先確認系統沒有一上線或一啟動就「冒煙」。

## Smoke Testing 在測什麼

Smoke Testing 通常只檢查最基本、最關鍵、最能代表系統是否可用的功能。

例如一個電商網站，可以檢查：

- 首頁能不能開啟
- 使用者能不能登入
- 商品列表能不能顯示
- 商品詳情頁能不能開啟
- 商品能不能加入購物車
- 結帳流程能不能走到付款前
- 後台或管理功能能不能登入
- 主要 API 是否回傳正常狀態

這些測試不一定會涵蓋所有細節，但會覆蓋「如果這些壞掉，整個版本就很難繼續測」的核心路徑。

## 什麼時候做 Smoke Testing

常見時機包括：

- 每次產生新的 build 之後
- 每次部署到測試環境、預備環境或正式環境之後
- CI/CD pipeline 完成部署後
- 做完整 Regression Testing 之前
- 修正重大錯誤後，先確認系統基本可用
- 修改環境設定、資料庫、外部服務串接後

一個典型流程可能長這樣：

```text
程式碼變更
  ↓
產生 build
  ↓
部署到測試環境
  ↓
Smoke Testing
  ↓
通過 → 進入更完整的測試
失敗 → 停下來修正 build 或部署問題
```

## Smoke Testing 的特性

好的 Smoke Testing 通常具備這些特性：

- 快速：最好在幾分鐘內完成
- 範圍小：只測核心功能，不追求完整覆蓋
- 結果明確：通過或失敗要很清楚
- 容易重複執行：適合放進 CI/CD 自動化流程
- 穩定：不要因為測試資料或環境小波動就常常誤報
- 能阻擋明顯壞掉的版本：失敗時應該暫停後續測試或部署

## Smoke Testing 和其他測試的差異

| 測試類型 | 主要目的 | 範圍 | 深度 |
|---|---|---|---|
| Smoke Testing | 確認版本是否基本可用 | 廣但淺 | 淺 |
| Sanity Testing | 確認某個修改或修復是否合理 | 窄 | 中等 |
| Regression Testing | 確認既有功能沒有被改壞 | 廣 | 較深 |
| Acceptance Testing | 確認是否符合使用者或業務需求 | 依需求而定 | 依需求而定 |

簡單記法：

- Smoke Testing：這個版本能不能繼續測？
- Sanity Testing：這個修正看起來合理嗎？
- Regression Testing：舊功能有沒有被改壞？
- Acceptance Testing：這個結果是不是使用者真正要的？

## 手動 Smoke Testing 範例

如果是一個 Web 系統，可以設計一份簡單清單：

```text
[ ] 網站首頁可以正常開啟
[ ] 使用者可以登入
[ ] 使用者登入後可以看到主要頁面
[ ] 主要列表資料可以載入
[ ] 可以新增一筆基本資料
[ ] 可以查詢剛剛新增的資料
[ ] 可以登出
```

這種清單適合在早期、系統還不穩定，或尚未建立完整自動化測試時使用。

## 自動化 Smoke Testing 範例

在 CI/CD 裡，Smoke Testing 可以自動執行，例如：

- 呼叫健康檢查 API
- 檢查首頁是否回傳 200
- 檢查登入 API 是否正常
- 執行幾個最重要的 E2E 測試
- 檢查服務是否成功連到資料庫
- 檢查外部依賴服務是否可用

自動化 Smoke Testing 的價值在於，它可以很早阻擋壞掉的 build，避免團隊把時間浪費在一個根本不能正常啟動的版本上。

## 常見誤解

### Smoke Testing 不是完整測試

Smoke Testing 通過，只代表系統的主要功能看起來能跑，不代表系統沒有 bug。

它比較像是「進入正式測試前的門檻」，不是測試工作的終點。

### Smoke Testing 不應該太多

如果 Smoke Testing 包太多測項，它就會變慢、變脆弱，最後失去「快速判斷版本是否可測」的價值。

比較好的做法是只保留最關鍵的流程，把其他細節交給 Regression Testing、Integration Testing 或 E2E Testing。

### Smoke Testing 失敗通常要優先處理

如果連最基本的功能都失敗，通常代表目前版本或環境有比較根本的問題。

這時候繼續做深入測試的效益通常不高，應該先修正讓 Smoke Testing 通過。

## 筆記小結

Smoke Testing 是一種快速、淺層、以核心功能為主的測試，用來確認新版本或部署結果是否基本可用。

它最重要的價值是幫團隊提早發現「這個版本根本不能測」的情況，讓後續測試、除錯和部署流程更有效率。
